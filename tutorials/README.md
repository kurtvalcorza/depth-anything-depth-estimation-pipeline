## Conformance notes

_Requirement identifiers in these notes (for example `ST1`, `PAR3`, `DAT24`, `EVAL21`) are the NOTEBOOK_SPEC 1.1 numbering they were written against; NOTEBOOK_SPEC 2.0 renumbered its sections and the pull request that migrated this repository reports conformance against the 2.0 pre-flight checklist (§26) and report format (§30)._

- **Standalone carrier (ST1–ST6):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/depth_anything_depth_estimation_pipeline/pipeline.py` verbatim (tagged `metadata.dimer.embedded_module`; the only rewrite makes the default weights directory working-directory-relative), Section 3 carries the model identity and the 4-file SHA-256 manifest inline (99 MB total) and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the generating revision, the module's SHA-256, and the generator version.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Model acquisition:** `stage_missing_files(WEIGHTS_DIR, allow_download=True)` fetches only the manifest entries that are absent, from the Hugging Face Hub at the immutable revision (never `main`); `verify_snapshot` re-hashes every entry; `from_pretrained(weights_dir=WEIGHTS_DIR)` then loads with `local_files_only=True` and `trust_remote_code=False`, so no remote model code is executed and there is no silent fallback to a different download. The notebook's only external dependencies are the pinned PyPI distributions and the Hub at that revision, and it never calls `huggingface_hub` itself.
- **Role stages:** `validate_inputs` (DAT24) writes `outputs/depth_anything_depth_estimation_input_manifest.json` with the schema, ceilings, per-input identifier, mode, size and aspect ratio, verdict, and one recorded rejection finding; it routes every image through the same public `validate_image` that `predict` calls, so the two cannot diverge. `evaluation_report` (EVAL21) writes `outputs/depth_anything_depth_estimation_evaluation_report.json` — `not-measurable` on the synthetic sample, naming the metric depth map that would make the task measurable, and `sample-sanity` with `abs_rel` (align=True, affine alignment in inverse depth) when the caller supplies one.
- The default sample is synthetic (a 320 x 240 luminance ramp with two drawn shapes, generated in code); it has no ground-truth depth, so the run is plumbing/sanity evidence only.
- The output is relative inverse depth (larger = nearer, unknown scale and shift), never metric depth; the notebook states this before, during, and after inference and surfaces `MIN_IMAGE_SIDE`, `MAX_IMAGE_SIDE`, and `MAX_ASPECT_RATIO` before the model runs.
- `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog.
- Recorded `SHOULD` deviation: EVAL11 (no trivial baseline — one cannot be scored without ground truth, which the default sample lacks; the evaluation report names the constant-depth and vertical-gradient priors a caller with ground truth should use).
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
